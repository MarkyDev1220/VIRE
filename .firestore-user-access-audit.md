# Firestore user profile access audit

Scope: migrate cross-user profile reads away from `users`, which stores account PII.

## Data model

- `users/{uid}`: private account/profile document; includes email, date of birth, gender, first and last name, username, profile fields, and account age acknowledgment.
- `users/{uid}/blockedUsers/{blockedUid}`: the owner's block list.
- `publicProfiles/{uid}`: signed-in user directory document. Allowed fields: uid, username, usernameLowercase, favoriteGames, favoriteGenres, skillLevel, localArea, gamerBio, aboutMe, profileImageUrl, coverImageUrl. It must not contain email, date of birth, gender, first/last name, or other private account fields.

## Access paths found

- Private owner reads: MainActivity startup/login; HomeActivity username refresh; ProfileActivity self view; SettingsActivity; TrustSafetyManager block list; CommunityDetailsActivity reads the current user's avatar.
- Private owner writes: SignupActivity creates a user; ProfileActivity edits profile/theme/image fields; SettingsActivity edits settings; TrustSafetyManager edits the owner's block list.
- Cross-user reads migrated to `publicProfiles`: SearchActivity, FriendManager search/notification name, FriendsActivity friend and request display, UserManager, PlayerFinderActivity, MessagesActivity, NewMessagesActivity, TournamentDetailsActivity, and ProfileActivity when viewing another user.
- Username/password sign-in now uses email only. Looking up an email from a public username would expose private account data; a secure username sign-in requires a trusted server flow.
- Other collections remain under their current rules: collections, communities, communityPosts, deckComments, friends, friendRequests, gameNights, gamingLocations, globalPosts, notifications, postComments, reports, storeReviews, tournamentMatches, tournaments, userDecks. Their CRUD calls were inventoried separately from this focused user-document policy change.

## Authorization intent

- Only the owner reads or writes `users/{uid}` and its blockedUsers subcollection.
- Any authenticated user may read `publicProfiles` for directory/search screens.
- Only the owner may create/update/delete the matching public profile; its schema is allowlisted and validates UID, strings, lengths, and list sizes.
- Existing accounts are copied to their own public profile document on successful sign-in. Users who have not signed in since deployment will not appear in the directory until they do.
